# INC-002 Nginx 强缓存命中旧资源，前端改动"永远不生效"

| 项 | 内容 |
| --- | --- |
| 编号 | INC-002 |
| 日期 | 2026-10 上旬 |
| 等级 | P2（功能异常，非中断） |
| 影响面 | 所有未强制刷新的浏览器，表现为"代码改了但页面没变" |
| 状态 | 已修复 |

## 现象

修改前端后执行部署，刷新页面仍是旧界面。表现为：

- 部分机器正常、部分机器是旧的，**清缓存后才对**；
- 一度怀疑是部署脚本没同步，反复重部署仍无效；
- 用 curl 直接取文件，内容却是**新的**。

## 排查过程

1. `curl` 取 `app.js`，内容已是新版本 → 服务器上的文件是对的，问题在浏览器侧。
2. `curl -I` 看响应头：

```
Cache-Control: public
Expires: <7 天后>
```

3. 确认 Nginx 配置对静态资源统一 `expires 7d`，**包括入口 `index.html`**。
4. 关键点：入口 HTML 被缓存 7 天，它里面引用的仍是旧的 `app.js` URL，
   于是即使 `app.js` 本身更新了，浏览器根本不会去请求它。

## 根因

缓存策略一刀切。入口 HTML 是"清单文件"，它决定要加载哪些资源，
一旦清单本身被强缓存，后面所有资源更新都失效。这不是缓存没生效，而是**缓存生效得太彻底**。

## 修复

按资源类型分级：

| 资源 | 策略 | 原因 |
| --- | --- | --- |
| 入口 HTML | `Cache-Control: no-store` | 每次都要拿到最新的资源清单 |
| JS / CSS | `expires -1`（协商缓存） | 每次带 `If-Modified-Since` 回源校验，没变走 304，开销可忽略 |
| 图片等强缓存资源 | `expires 7d` + URL 带 `?v=版本号` | 靠版本号变更触发重新拉取 |

## 验证

改一版前端 → 部署 → 直接用浏览器普通刷新（不按 Ctrl+F5）→ 界面立即更新为最新。

## 预防

- 入口 HTML 永远不参与强缓存，这是硬规则；
- 强缓存资源必须版本化，否则等于给未来的自己埋雷；
- 发布后不要用"我这边是好的"来下结论，`curl -I` 看响应头比刷新页面可靠。

## 经验

> 缓存问题的典型特征是"有的人好、有的人坏，清缓存就好"。
> 一旦出现这个组合，先看响应头，不要先怀疑发布流程。
