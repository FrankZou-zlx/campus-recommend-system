# 故障复盘索引

系统在开发与部署过程中实际发生的 5 起故障，全部按「现象 → 排查 → 根因 → 修复 → 预防」记录。
这些不是推演出来的案例，每一起都对应仓库里的一处改动。

| 编号 | 标题 | 等级 | 一句话根因 |
| --- | --- | --- | --- |
| [INC-001](INC-001-deploy-script-source-deleted.md) | 部署脚本在部署目录执行，源码被删除 | P1 | `SRC==DST` 时 `rm -rf` 先删源再复制，必然失败 |
| [INC-002](INC-002-nginx-cache-stale.md) | Nginx 强缓存命中旧资源，改动不生效 | P2 | 入口 HTML 也被缓存 7 天，资源清单永远指向旧文件 |
| [INC-003](INC-003-mysql2-length-check.md) | 单行结果判空写法错误，发货接口恒拒绝 | P2 | 对象没有 `length`，`!row.length` 恒为真 |
| [INC-004](INC-004-smtp-ehlo-missing.md) | SMTP 465 未发 EHLO，告警邮件发不出 | P1 | TLS 握手完成 ≠ SMTP 会话握手完成 |
| [INC-005](INC-005-category-id-drift.md) | 分类自增 ID 漂移，商品显示「未分类」 | P3 | 删分类不查引用 + 自增计数未重置，留下悬空外键 |

## 共同特征

这五起里有三起（002、003、005）属于同一类：**系统不报错，功能却不对**。
它们不会触发异常、不会写进错误日志，只会在某个页面上安静地表现出"少了一个字段"或"每次都不成功"。
这类问题最考验排查方法——不是看日志，而是先确认"数据和代码到底哪一侧错了"。

另外两起（001、004）则说明另一件事：
**自动化的破坏力和自动化程度成正比**，脚本能省下的时间，也能在一次误操作里全部还回去；
而**监控自身的可靠性也必须被验证**，没做过告警演练的监控等于没有监控。

## 怎么用这份材料

- 面试时不用展开讲，直接让对方看编号目录，挑一个他感兴趣的；
- 每个复盘里都有具体报错、具体命令、具体文件行号，可以当场对照代码；
- 「预防」一节写的是改了什么，不是"以后会注意"这类空话。
